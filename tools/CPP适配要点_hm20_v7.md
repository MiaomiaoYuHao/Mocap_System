# C++ 侧适配 hm20_v7（姿态版）

## 零、最小改动是「不改」

新模型的输出**全部追加在尾部**，索引 0~5 跟 v6 一模一样：

```
0 log_assign   (1,N+1,21)   ┐
1 pos          (1,20,3)     │ v6 就有，位置和语义完全不变
2 center       (1,3)        │
3 scale        (1,1,1)      │
4 ghost_logit  (1,N)        │
5 miss_logit   (1,20)       ┘
6 joint_ang    (1,20)       弧度，5指×4维      ┐
7 hand_logit   (1,)         >0 判右手           │ 新增
8 pose_conf    (1,5)        逐指姿态置信度      │
9 seg_rot6d    (1,16,6)     分段朝向的6D表示   ┘
```

而 `Hm20OnnxBackend.hpp` 已经做对了两件关键的事：

- `Run()` 传的是 `kOnnxOutputNames()`，**onnxruntime 支持只请求输出子集**
- `verifyContract()` **按名字查**，不数个数（注释里写着这正是上次踩坑的根因）

所以换上 v7 的 onnx，现有代码原样能跑，只是拿不到新能力。

## 一、手性自动判定（收益最大，改动最小）

**训练集准确率 98.5%。** 这直接替掉 `Hm20AutoCalib` 里那套几何判据——那套依赖拇指标签（全手最容易丢和误配的球，可见率只有 45%），实测经常错判。

### 改动

`Hm20OnnxBackend.hpp`：

1. `kOnnxOutputNames()` 加 `"hand_logit"`
2. 结果结构加 `float handLogit = 0.f; bool hasHand = false;`
3. `run()` 里按请求顺序读对应的 `res[i]`

### 用法（关键）

**手性是会话常量，不要每帧信。** 建议：

```cpp
// 连续 N 帧一致才更新，之后锁定；跟 WristHold 同一个模式
if (inf.hasHand) {
    const bool r = inf.handLogit > 0.0f;
    if (r == handVote_) { ++handVoteN_; } else { handVote_ = r; handVoteN_ = 1; }
    if (handVoteN_ >= 30 && !handLocked_) { handIsRight_ = r; handLocked_ = true; }
}
```

面板的「右手」开关改成**自动检测 + 手动覆盖**：自动判定只在用户没有手动设置时生效，手动设了就以手动为准（保留 `Hm20AutoCalib` 现有的 `applyHandedness=false` 语义）。

## 二、姿态直接用，绕开几何链（核心价值，但必须先验证）

### 为什么值得做

现在 M3DQ 的分段四元数是 `boneFrame` 从 marker 位置**做差分**算的。而中节两球基线只有 **40~55mm**：

```
两端各偏  7mm  →  骨轴偏 20°
两端各偏 15mm  →  骨轴偏 40°
```

而遮挡点的位置误差本来就是 10~30mm 量级。仿真实测（真模型闭环、3相机、32%遮挡）：

```
遮挡时中节骨轴误差   中位 21.4°   p90 55.2°   max 107.9°
```

**`seg_rot6d` 不做差分**，直接回归朝向，训练集姿态误差 7.30°。

### 但先验证，不要直接换

用 `tools/sim_jitter.py`（已经能加载 onnx），量遮挡帧的骨轴误差，跟上面那组 21.4°/107.9° 比：

- **能到 7~10°** → 碾压性改善，值得换
- **只到 20°** → 打平，姿态头的价值主要在"不用标定"而非"更准"

**没有这个数之前不要动几何链。** 仿真和真机之间这个项目已经吃过好几次亏（比如"融合外推"在逐点位置指标上全赢、骨轴方向却从 21.4° 劣化到 40.5°）。

### 6D 转旋转矩阵

`seg_rot6d` 是旋转矩阵的**前两列**，Gram-Schmidt 补出第三列：

```cpp
// 参考 net.py 的 _6d_to_mat
Vec3 a{x[0],x[1],x[2]}, b{x[3],x[4],x[5]};
Vec3 e1 = normalize(a);
b = sub(b, mul(e1, dot(e1,b)));
Vec3 e2 = normalize(b);
Vec3 e3 = cross(e1, e2);
// 列 = e1,e2,e3
```

**为什么训练侧用 6D 不用四元数**：四元数有双覆盖（q 和 −q 同一个旋转），直接回归会在符号边界撕裂——C++ 侧已经在 `alignQuatHemisphere` 上处理过同类问题。6D 表示连续、无歧义。

### 融合而不是二选一（推荐）

`pose_conf`（逐指置信度）让你可以按场景选：

| 场景 | 信谁 | 依据 |
|---|---|---|
| 三颗球全可见 | **几何** | 实测张开手时中节相对近节 5° 以内，比 AI 的 7.3° 好 |
| 部分遮挡 | 按 `pose_conf` 加权 | 它的监督目标就是"该指有几个 marker 可见 / 3" |
| 全遮挡 | **AI** | 几何链此时是 21.4°/max 107.9° |

这比整条链替换风险低得多，而且能同时拿到两者的长处。

## 三、关节角的维度不一致（必须映射，不能直接塞）

```
模型 joint_ang    20 维 = 5指 × 4维（拇指也是 4 维）
C++  M3DS         16 维 = 拇指4 + 四指各3
```

这是**两套约定**，训练侧跟 `pose_prior.py` 的 `(5,4)` 对齐，C++ 侧是下游协议。

模型的 20 维语义（来自 `pose_prior.py` 第 30~33 行）：

```
拇指   [CMC屈, CMC展, MCP屈, IP屈]
非拇指 [MCP屈, MCP展, PIP屈, DIP屈]
```

C++ 的 16 维少的是四指的 DIP（因为 DIP 和 PIP 强耦合，下游用耦合系数推）。所以映射是：

```
M3DS[0..3]   = joint_ang[0..3]           拇指 4 维直接对应
M3DS[4+3f+0] = joint_ang[4+4f+0]         MCP屈
M3DS[4+3f+1] = joint_ang[4+4f+1]         MCP展
M3DS[4+3f+2] = joint_ang[4+4f+2]         PIP屈
                joint_ang[4+4f+3]         DIP —— 丢弃或用来校验耦合
```

**注意符号约定**：C++ 侧这轮修过 PIP 的符号（`Hm20JointAngles.hpp` 里 hinge 从 `cross(a0,ẑ)` 改成 `cross(ẑ,a0)`），还有左手镜像时 flexion 维取反。**模型输出的是 rig 的原始约定，接进去之前要对齐**，否则会出现"握拳时 PIP 是负的"这种老问题。

建议：先在 `HandOutputMonitor` 面板上**并排显示**模型的 20 维和几何算的 16 维，肉眼确认符号和量级对得上，再接进 M3DS。

## 四、匈牙利指派（白赚 3.78 点整帧）

```
frame  56.57%   直接 argmax
hframe 60.35%   匈牙利全局最优分配
```

逐点几乎没差（`acc` 92.60% vs `hung` 92.65%），说明错误不是分配冲突而是真判错了。但**整帧救回 3.78 点**——整帧只要错一个点就废，匈牙利能把"差一点就全对"的帧补回来。

代价是每帧一次 20×N 的分配求解，几十微秒量级。

（v6 的 `hung_frame` 是 55.66%，现在 60.35%，**这是少数明确超过 v6 的指标之一**。）

## 六、建议的实施顺序

1. **换 onnx，什么都不改** —— 确认现有功能不退化（契约检查会打印 I/O，看到 10 个输出即正常）
2. **接手性** —— 改动最小、收益立刻可见、风险几乎为零
3. **跑 `sim_jitter.py` 量姿态** —— 拿到遮挡帧的骨轴误差再决定第 4 步
4. **姿态融合**（不是替换）—— 按 `pose_conf` 在几何和 AI 之间加权
5. **匈牙利指派** —— 独立改动，随时可做

**第 3 步是分水岭。** 没有那个数就动几何链，等于重复这个项目已经犯过好几次的错误：在仿真指标上赢、在真机上输。

---

## 七、几个绝对不能动的约定

- **输出顺序** —— C++ 按位置取 `res[i]`，新输出只能追加在尾部。哪天重新导出时插在中间，所有旧代码会静默错位（不报错，只是全错）
- **`tmpl_valid` 的第 1 轴必须是动态的** —— C++ 发的是 `(1,1)`，训练用的是 `(1,20)`，导出成固定 20 会让 ORT 直接硬报错。`train.py` 的 `dynamic_axes` 里已经处理
- **`verifyContract()` 按名字查，不要改回数个数** —— 文件里的注释写明了这是上次踩坑的根因
