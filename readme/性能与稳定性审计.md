# 我的改动对性能和稳定性的影响 —— 实测审计

不给"没影响"这种话。逐项量，包括我自己惹的麻烦。

---

## 一、性能：查出一个我低估的东西，已修

`DorsumRigidSolver::solve()` 每帧都跑，我原来以为它"远低于一次推理的 1%"。**实测不是**：

| 场景 | 修之前 | 修之后 |
|---|---|---|
| 20 候选点（你的典型值） | 0.893 ms | 0.791 ms |
| 26 候选点 | 2.345 ms | **0.725 ms** |
| 32 候选点 | 2.937 ms | **0.961 ms** |
| **32 点全挤在手背附近（剪枝失效）** | **24.784 ms** | **1.175 ms** |

最坏情况 **21 倍**。而且这是 Release —— 你的 Debug 构建要再乘 3~10 倍，
也就是说原来最坏能到 75~250ms，**跟你看到的 280ms 尖峰同一个量级**。

### 原因和修法

种子搜索是 O(模板对 × 候选对)，剪枝靠"边长对不上"。一旦杂点挤在手背附近
（反光、另一只手、贴球聚团），剪枝全失效。

两道闸：
1. **空间门控** —— 有上一帧位置时只看它 70mm 内的点。手背一帧动不了那么远，
   这一刀通常把 32 个候选砍到 6~8 个。这是主要提速来源。
2. **种子数硬上限 400** —— 兜住①也失效的病态帧（冷启动 + 杂点聚团）。
   宁可这一帧解得糙，也不要单帧堵住流水线。

⚠️ 门控引入了一个坑我顺手堵了：`pointOf` 返回的是**门内下标**，
调用方拿它索引原始点云会取到不相干的点。这种错不会崩，只会让手背标签
静默指向错误的点 —— 已加映射回原始下标。

### 准确率回归

蒙特卡洛 400 次/组，跟优化前**逐行一致**：

```
0.9mm 噪声 有历史:  正确 1.000  错标 0.000  拒解 0.000
0.9mm 遮挡2 杂点10: 正确 0.953  错标 0.015  拒解 0.033
```

贴点重捕仍然 84 帧恢复 5/5，3 种误触发场景仍然 0 误修。

Ready 之后按 shot 增量退避（多 12 个才重跑）。

## 四、稳定性：三个真实风险，按大小排

### 🔴 `chainContinue` 默认 false → true

这是**最大的风险**。这个开关关着的时候 `continueChainForOccluded()` 整个函数是死代码 ——
也就是说那几百行**从来没在生产里跑过**。现在打开了。

我做了什么：拇指那一支重写并用两段真实录制验过（17 段遮挡）。
但**四指那一支我没动，也没有真机验证**。四指的中远节现在会走这条路。

怎么兜：出问题就把 `Hm20Config::chainContinue` 改回 `false`，
立刻退回你之前的行为（遮挡点退回网络 pos 头）。这是一行。

### 🟡 贴点重捕会改模板，而且是持久的

一次错误的重捕会污染模板，且原来没有回头路。已加：三道安全闸
（散布 < 2.5mm、新位置不能太靠近别的点、改完自歧义不能塌）+ 看门狗 + 「手背复位」按钮。

但**我没能构造出你说的那个"连线全乱"场景**，所以不敢说这些一定够。
面板上有 `模板已被重捕改动XXmm`，这个数很大而画面是乱的，就是它出问题了。

### 🟡 `pronLocked_` 一旦锁死，整个会话不再重搜

如果第一次自信拟合（对比度 ≥3）是错的，就锁进去了。
兜底是重新标定。我认为值得 —— 每秒 250ms 的卡顿代价更大。

| | |
|---|---|

## 建议

1. **先换 Release 构建**，零风险，而且我上面所有数字在 Debug 下都要重量
2. 覆盖 `DorsumRigidSolver.hpp` + `Hm20AutoCalib.hpp`（这两个是纯性能修复，准确率验过没掉）
3. 跑一段长的（2~3 分钟），看耗时有没有随时间涨 —— 那是我现在看不到的
4. 四指如果开始出怪角度，第一件事是把 `chainContinue` 改回 false 确认是不是它
