# 相机添加这条线：又查出三个

前一条消息修了两个（COM 套间 / 关闭途中建相机）。你让我继续查，
在同一条线上又找到三个，**其中两个是"不会崩但会给错结果"的那种**。

---

## ④ 已添加的相机不会被置灰 → 会重复添加同一台

```cpp
const QString key = "web:" + QString::fromLatin1(d.id);   // DirectShow DevicePath
if (used_.contains(key)) { ...置灰... }
```

而 `used_` 里的 key 是 `"web:" + QCameraDevice::id()` —— **Qt 的 id**。

两者都是内核符号链接，但**不保证逐字节相同**：Qt 走 Media Foundation 时
编码方式可能不同，大小写和前后缀也不一定一致。

**这个我自己在 `onAccept()` 里已经知道了** —— 那里写的是"互相包含 + 退回友好名"
的匹配。但列出列表时却直接 `contains()` 比字符串，前后不一致。

改成 `isUsed()`，用同一套宽松匹配。

## ⑤ 刷新时按行号恢复选中 → 会选到另一台相机

```cpp
const int prevRow = list_->currentRow();
... list_->clear(); 重建 ...
list_->setCurrentRow(prevRow);
```

**刷新的原因恰恰是列表变了。** 插一个相机导致重排时，同一个行号指向另一台设备。
用户选好了、一秒后自动刷新、选中项静默换成别的，然后点确定加错相机。

改成按设备 id 记住和恢复；找不到（设备被拔了）就不选，让用户自己重新挑 ——
总比默默选中一台别的强。"虚拟测试相机"没有 id，单独用一个标记。

## ⑥ 延迟调用把"设备失效"的窗口变大了

我上一条加的 `QueuedConnection` 是必要的，但它有副作用：用户点确定之后、
lambda 执行之前，设备可以被拔掉。而 `addWebcam` **无条件 `nextId_++` 并 `start()`**，
不检查设备有效性 —— 结果是一个跑不起来的空相机占着位置，还得手动删。

原来模态那版这个窗口极小（`exec()` 返回后立即执行），是我把它拉大的。
加了 `dev.isNull()` 检查 + 提示。
