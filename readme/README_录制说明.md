# ROM 标定 v2 + 录制链路补齐

## 一、根因（先看这个，后面的改动都是围着它转的）

不是四元数错了。你验证四元数是对的，这个判断成立 —— **坏在从四元数取角时选错了骨轴**。

`HandSkeletonAssociator::computeSegmentQuats()` 里近节骨轴有两条来源：

```cpp
dirProxUse = dirProx;                                  // = pp球 -> mp球   ← 退化
if (f != 0 && anchorsValid && out.wristPoseValid)
    dirProxUse = pp球 - anchor;                        // 正确的近节骨
```

而 `solveJointAngles()` 里算 PIP 的第二条轴 `a1` **恒等于 `pp球 -> mp球`**。

三个条件任一不满足，`a0` 和 `a1` 就是同一个向量，`PIP = acos(1) = 0`。不是不准，是**结构性的零**：

- **拇指**：`f != 0` 恒为假 → **拇MCP 从来没工作过**，输出恒为 0
- **四指**：`wristPoseValid` 为假时退化 —— 而握拳恰恰是手背最容易被四指挡住的时候

一条解释三个症状：

| 症状 | 成因 |
|---|---|
| 覆盖度卡在 50% 上下 | PIP 样本是「真实屈曲值」和「恒零」的混合，p2 落 0、p98 落中间值，`(hi-lo)/1.92` 差不多正好一半 |
| 握拳少、张开满 | 混合里握拳端反而更接近 0；ROM 归一化 `u=(q-lo)/(hi-lo)` 对方向完全无知，反向信号映射完还是反的 |
| 四元数对得上、角度对不上 | 四元数确实对，坏在取角的轴选取上 —— 所以「验证四元数」这条路查不到它 |

还有第二处：`solveJointAngles` 在腕部系失效时**只更新 PIP、MCP 保持上一帧**，却仍然置 `fingerValid=true`。ROM v1 照着逐指的 `fingerValid` 采样，把大量「张开时的 MCP 值」当成握拳样本收了进去。

## 二、改了什么

### 新增 `src/estimate/RomCalibration.hpp` —— ROM 引擎 v2

自包含，零 Qt 依赖，可单独编译进测试程序。

1. **逐维、逐帧判样本可用性**，拒收原因分 6 类计数（不是静默丢弃）
2. **方向自动判定**：用卷曲度 `curl = |pp→dp| / (|pp→mp|+|mp→dp|)` 当参考。它只用球心间距算，不经过腕部系/四元数/anchor，上面那些退化一条都影响不到它。方向 = 握拳端中位 − 张开端中位的符号（比相关系数稳，因为端点停留短、中间过渡长）。区间定义在带符号空间 `v = sign*q` 上，于是「屈曲 → 输出变大」恒成立
3. **按 curl 外推**：握到底那段角度物理上就没有，但 curl 有。拿可见段拟合 `v = a + b·curl` 外推到 curl 真实端点。三道闸限着：R² ≥ 0.55、可见段 curl 跨度 ≥ 0.25、外推量 ≤ 实测行程 60%，还要不超解剖限位
4. **两端相位分位 ∪ 全局 p2/p98**：并集只会让行程更满，而两者各自都是分位数，野点仍然进不来
5. **标不满的维按先验兜底**，而不是留 `lo=hi=0` —— 留 0 会让映射走透传+钳位，把带常量偏置的原始角直接钳进目标行程，那是 100% 触限
6. **死维冻结在解剖中立位**，不是钳到行程端点（钳到端点对屈曲维就是「一直伸直」或「一直握死」，后者是危险动作）
7. **运行时退化帧保持上一帧输出**，不把 `PIP≡0` 发下去
8. **支持补标**：按住 Ctrl 点「ROM标定」= 保留上一轮样本，只针对没标满的维再做一次动作，已标好的按「取更好的那份」合并

### `Hm20JointAngles.hpp` —— 加 `JointSolveDebug` 纯出参

默认 `nullptr`，不传时一条指令都不多执行，**现有输出逐位不变**。导出：两条骨轴、`dot(a0,a1)`、铰链符号、三个提取式的原始输出、`proxAxisSrc`、curl、以及**逐维**的 `dofState`。

v1 的 `RomCalibrator`/`RomMapper` 标了 `[[deprecated]]` 但保留，方便 A/B 对照。

### 录制格式 v7 —— 加两块 + 四个事件码

| 块 | 内容 |
|---|---|
| **31 RomCalib** | ROM 逐维全量：样本数、逐原因拒收数、方向及其判据、两端相位中位、拟合斜率/R²、外推量、状态码。写入时机：开始 / 标定中 1Hz / 结束 |
| **32 JointSolve** | 逐帧解算内部量：两条骨轴、`dotProxMid`、铰链符号、`proxAxisSrc`、curl、逐维 `dofState`、逐维采样判决 |

事件码：`16` 按下 ROM标定、`17` 按下结束ROM（GUI 线程墙钟）、`18`/`19` 采样真正起止的那一帧（worker 侧）。

**16/17 和 18/19 分开记**是有意的：按钮回调在 GUI 线程，`romLearning_` 是原子标志，worker 要到下一帧才读到，中间隔着投递延迟。只记按钮会对不上帧号，只记帧又对不上你「我什么时候按的」。两个都记，差值本身还能反映 worker 积压。

按下结束时，整份人类可读报告也会走 `ParamDelta` 落盘。

### `tools/pcrec/pcrec.py`

解析新块。**顺带修了一个现存 bug**：C++ 的 `IkDbgRec` 是 680 字节（后来加了 MCP-PIP 耦合那五个数组），而 py 的 dtype 还是 608。后果不是报错 —— `_take()` 对账发现不等就**整块跳过**，也就是说 **IK 内部那一路在你之前所有分析里一直是空的**，而 summary 显示 `IK内部 0` 看起来就像「这次没录到」。

### `tools/pcrec/rom_report.py`（新）

五节报告：骨轴退化率 → ROM 事件时间轴 → 逐维标定明细 → 标定期间状态分布 → 四级流水。

## 三、验证情况

`tests/test_rom_calibration.cpp`，7 个场景全过：

```
场景 B+C（握拳腕部系失效 + PIP 骨轴退化，复刻真机）
  v1 覆盖度 63.1%  →  v2 覆盖度 86.7%（达标 11/11）
场景 D（方向整段相反）
  v1：张开端 0.99、握拳端 0.01   ← 复现「握拳少、张开满」
  v2：判出 sign=-1，映射后握拳端 1.90 rad > 张开端 0.02 rad
场景 E（拇MCP 结构性恒零）
  v2 判成 AxisDead 并冻结在中立位，而不是悄悄「标定成功」
```

另外造了一个合成 v7 `.pcrec` 跑通了 **C++ 结构体 → py dtype → 报告脚本** 的完整链路，尺寸逐字节对上（RomCalibRec=2040、JointSolveRec=504）。

```bash
g++ -std=c++17 -I src tests/test_rom_calibration.cpp -o /tmp/t && /tmp/t
```

## 五、录制怎么做

### 开关

- 录制详细度选 **Full**（块 32 受 `wantsFull()` 限制；块 31 不受限，任何档位都写）
- 其余开关保持你平时的设置**别动** —— 这次要看的是常态下的表现

### 第一段：ROM 标定

1. 先点「● 录制」
2. 再点「ROM标定」
3. 五指张开到底 → 握拳到底，**来回三遍，慢一点**，每端稍微停一下（相位分位靠端点停留）
4. 点「■ 结束ROM」，**把弹窗里「显示详细信息」展开截个图**
5. 停止录制

### 第二段：标定后

1. 重新点「● 录制」
2. 做几个动作：慢速开合、单指屈伸（食指、中指各来一次）、握拳保持 3 秒、张开保持 3 秒
3. 停止录制

两段都发过来，我跑：

```bash
python3 tools/pcrec/rom_report.py 标定段.pcrec 标定后段.pcrec
```

### 现在就能自己先看一眼的

不用等我 —— 把手背朝相机慢慢握拳，盯着面板上 `wristPoseValid` 的掉线比例：

- 握到底那段基本是 0 → **外推是必须的**，就是上面 86.7% 那条路
- 大部分时间还在 → 退化主要来自 `anchorsValid`（anchor 自检没过），修法完全不同：`verifyAnchors` 是个**一次性锁**，判过一次永不重试，得看 ChainDbg 的 `anchorsVerifyNSeen/NOk`

这个数直接决定后面要不要动上游取轴。

## 六、还没动的：上游取轴

`拇MCP 恒为 0` 这一条 ROM 层救不了 —— 没有信号可标。真正的修法是让 `computeSegmentQuats` 在腕部位姿失效时用**保持的腕部位姿**（`WristHold` 里已经有 R 了），或者给拇指单独走 anchor 路径。

我没动它，因为那会改变现有输出，超出「只改 ROM 这部分」的范围。等你的素材回来，`proxAxisSrc` 的分布会直接告诉我们值不值得动、以及动哪一处。
