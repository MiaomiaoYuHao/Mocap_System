# 一、roll 改成沿链继承（做完了）

## 先撤回我上一条的结论

我说"扭转中位 0.2°，说明 roll 准"——**那是循环论证**。
纯屈曲时旧构造算出的扭转**恒等于 0.0000°**，跟真骨长什么样毫无关系：
两节骨都用同一个参考（手背法向）做 Gram-Schmidt，纯屈曲时两个 y 轴天然平行。

## 改法

```
手背(5 点，3 自由度，真的可测) -> 近节 -> 中节 -> 远节
每一级只做最小旋转(swing，不含 twist)对齐骨轴，roll 原样带下来
```

这正对应"关节是单弯曲轴"——你说的那个。

**实测对比**（外展出平面 15°，近节-远节之间的假扭转）：

| 近节屈曲 | 旧：独立构造 | 新：沿链继承 |
|---|---|---|
| 20° | **10.21°** | **0.00°** |
| 40° | **40.61°** | **0.00°** |
| 60° | **73.69°** | **0.00°** |
| 80° | **28.88°** | **0.00°** |

纯屈曲时两者都是 0（旧构造在这种情况下本来就对）。

## 顺带更正：退化分支我高估了

查了两段真实录制共 12149 个段样本，骨轴落进退化区（与手背法向夹角 < 8.6°）的
只有 **3 个 = 0.04%**。所以那个 172° 的 max **不是退化造成的**，
就是外展造的假扭转（60° 屈曲 + 15° 外展已经能到 73.69°）。

新构造不依赖手背法向，退化分支连同它一起消失了。

开关 `Hm20Config::chainRoll`，默认 `true`，会记进 `.pcrec` 文件头。
拇指的 CMC 旋前仍然单独补，因为那一维是真实自由度。

**关节角不受影响** —— `Hm20JointAngles` 只取段坐标系第 1 列（骨轴）算屈曲/外展，
roll 怎么定都不进那个式子。变的是 M3DQ 输出的四元数本身。

# 二、"单线程"那个推断：确认了，而且是默认值

```cpp
explicit Hm20OnnxBackend(const std::string& modelPath, int intraOpThreads = 1)
                                                                          ^^^
```

**默认就是 1，而调用方一直没传第二个参数。** 你的 30ms 跟本机单核实测 26.2ms
几乎一致，就是这个原因。

现在改成传物理核数（`idealThreadCount()/2`，超线程那一半对这种算子密集的图
基本没收益还抢缓存）。**这一项不改变任何数值结果，纯免费提速。**

# 三、高速模式（INT8）—— 加一条路，不替换原链路

## 怎么用

1. **把 `hm20_v7_int8.onnx` 放在 `hm20_v7.onnx` 旁边**（你截图里已经放好了）
2. 重新编译运行
3. 点云面板的「IK精修手指姿态」旁边会多一个 **「高速模式(INT8)」** 勾选框
4. 勾上即切换，不用重启

**找不到 INT8 文件时勾选框会灰掉并显示「高速模式(未找到INT8模型)」** ——
不静默失败。

命名约定：`xxx.onnx` -> `xxx_int8.onnx`。也可以用 QSettings 的
`hm20FastModelPath` 显式指定。

## 怎么确认切过去了

面板上新增一行：

```
推理：hm20_v7_int8.onnx   单帧 9.6ms
```

**模型名会显示出来**。切换失败会静默退回原模型，不显示的话你会以为切过去了、
然后困惑于为什么没变快。

## 实测数据（三段真实录制、360 帧）

| | |
|---|---|
| 单线程耗时 | 26.7ms -> **9.6ms** |
| 体积 | 140MB -> 36MB |
| 标签一致率 | **98.71%** |
| pos 误差 | 中位 0.95mm，p95 1.73mm |

**最关键的一条**：被改变标签的点，原模型自己的置信度中位只有 **0.370**；
没被改变的是 **0.968**。分歧只发生在模型本来就没把握的点上，
而那些点在关联器里本来就过不了 `minAssignProb` 门限。

**但遮挡多时分歧会变大**（遮挡压力段一致率 97.3%，逐帧最低 85.7%）。
所以建议先录同一段动作各一次对比 `pcrec_report.py` 里的三个数：
`dorsumReason` 分布、刚体不变量中位、`numGhost`。

# 四、提速总结

| 手段 | 幅度 | 影响数值吗 | 状态 |
|---|---|---|---|
| **多线程** | 未知（你那边一测就知道） | **不影响** | ✅ 已接，自动取物理核数 |
| **INT8** | **2.8x**（点少时 3.8x） | 影响，98.7% 一致 | ✅ 已接，勾选框切换 |
| `maxCandidates` 32->24 | 约 1.1x | 极小 | 未做，改一个数 |
| GPU (DirectML) | 估 3~8x | 不影响 | 未做 |

前两项做完很可能就到 5ms 以内了。GPU 那条我估 3~8 倍不是 20 倍 ——
34.8M 参数、3455 节点，里面 `Constant`/`Slice`/`Shape`/`Gather` 一大堆碎算子，
batch=1 时 kernel 启动开销占比很高。

# 六、复查发现的两个问题（已修）

你让我再检查一遍，查出两个，第一个是真的会咬人：

## ① 切换模型会把学习状态全抹掉

`ensureInitialized()` 里原本是 `assoc_ = make_shared<...>` —— **整个重建关联器**。
切换 FP32 <-> INT8 会走这条路，于是手背重捕修好的模板、连续性锁、
拇指跟随器学到的弯曲轴、`dipK_`/`mdLen_` 全部丢掉。

这跟几轮前查出来的"自标定推模板导致重捕全丢"是**同一个坑**，换模型时又踩一次。

而 backend 是无状态的（每帧独立推理，不跨帧携带任何东西），
根本不需要重建关联器。加了 `Hm20SkeletonAssociator::setBackend()`，
切换时只换那个指针，学习状态原样保留。

## ② diag 每帧构造 QFileInfo

模型文件名只在切换时变，却在 120fps 的路径上每帧做一次
`QFileInfo` 构造 + `std::string -> QString` 转换。改成切换时算一次、缓存起来。
