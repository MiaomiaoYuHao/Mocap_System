# INT8 量化 + "拇指那条线卡死"是什么意思

---

## 一、"拇指那条线卡死在这" 指的是这条依赖链

```
thumbPronation0 = -1.24 rad     ← 标定得很好（碗底对比度 11.7，我设的可信门槛是 2.0）
      ↓ 只被 markerFK 消费
   markerFK
      ↓ 只在 IK 里跑
   Hm20IkRefiner
      ↓ 需要 ikUsable() == true
   ikUsable() 要求 bundleRmseMm < 4.0
      ↓ 你的实测是 16 ~ 45 mm
   ✗ 永远不成立
```

**所以那个标定得很漂亮的数，一次都没被用上。** 拇指外翻的修复走的是另一条路
（`continueChainForOccluded` 的几何跟随），能挡住最糟的情况，但真正的解剖旋前补偿
一直没生效。

要通这条线，只能把 `bundleRmseMm` 压到 4.0 以内 —— 而它高的原因是**在
`rigid_motion` 段做的自标定**：手型固定、手指不动，锚点球面拟合本来就是退化的。
换到手指有屈伸的段重标一次，是唯一可能打通它的动作。

**IK 不生效的其余后果没那么严重**：姿态本身不亏（几何在观测充分时反而更准，
5° vs 7.3°），主要损失是**解剖限位没人拦**（截图里 PIP 出现 130°，限位 110°）。

## 二、INT8：会不会降低性能

**速度：**

```
体积      140 MB  ->  36 MB
单线程    26.7ms  ->  9.6ms     (2.8x；点数少时到 3.8x)
```

**精度（三段真实录制、360 帧）：**

| | |
|---|---|
| 标签一致率 | **98.71%** |
| pos 误差 | 中位 0.95mm，p95 1.73mm |
| joint_ang 误差 | ~1.5° |

**最关键的一条**——我专门查了"被改变标签的点，模型自己有多确信"：

```
标签【被改变】的点：FP32 置信度中位 0.370   (n=111)
标签【没变】的点  ：FP32 置信度中位 0.968   (n=5021)
```

**分歧只发生在模型本来就没把握的点上。** 而那些低置信点在你的关联器里本来就
过不了 `minAssignProbDorsum`(0.3) / `minAssignProbFinger`(0.55) 的门限 ——
也就是说被改变的那批，大多数本来就会被当成 ghost 丢掉。

### 但有一处要提醒

**遮挡压力那段一致率掉到 97.3%，逐帧最低 85.7%。**

遮挡越多、点越少，模型越不确定，量化的分歧就越大。这不是量化坏，
是"模型本来就在猜"的那部分被放大了一点。

所以我的建议是：**先并行跑一段对比**，别直接换掉。
你现在有 `.pcrec`，录同一段动作，一次用 FP32、一次用 INT8，
用 `pcrec_report.py` 比这几个数：

- `dorsumReason` 的分布（歧义拒解有没有变多）
- 刚体不变量的中位（端到端精度）
- `numGhost`（被丢掉的点有没有变多）

三个都没变差就可以换。

### 我用的是随机点时得出过完全相反的结论

第一次测我用 `np.random.randn` 造点，一致率只有 86.7%，差点就得出"INT8 不能用"。
换成你的真实点云才是 98.7%。**分布外输入的模型行为不能代表实际表现** ——
这条以后测别的东西也适用。

## 三、提速的建议顺序

1. **先设 `intra_op_num_threads`** —— 本机单核跑出 26.2ms，跟你的 30ms 几乎一样，
   强烈提示你的 ORT 在跑单线程。设成物理核数可能就是免费的 2~4 倍。
   本机只有 1 核，这条我量不了，你那边一试就知道。
2. **再上 INT8** —— 2.8~3.8x，已验证。
3. **`maxCandidates` 从 32 收到 24** —— 我更正一下上轮的说法：耗时**确实**随点数变
   （N=16→48 是 99→148ms），之前说"无关"是因为你的数据只在 16~21 这个窄区间。
4. **最后才考虑 GPU** —— 34.8M 参数、3455 节点，里面 `Constant`/`Slice`/`Shape`/`Gather`
   一大堆碎算子，batch=1 时 kernel 启动开销占比很高。我估 3~8 倍，不是 20 倍。
   DirectML 比 CUDA 好部署。

前两步做完很可能就到 5ms 以内了，GPU 就不必了。
