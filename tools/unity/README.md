# Unity 端接入

把 `MocapHandReceiver.cs` 拖进 Unity 工程，挂在任意 GameObject 上，
把手骨骼拖进 Inspector 的 `segments` 数组（16 个，顺序见下），运行即可。

默认监听 **127.0.0.1:9010**，跟发送端一致。

## 两种驱动方式，Inspector 里 `driveMode` 切换

| | JointAngles (M3DS) | Quaternion (M3DQ) |
|---|---|---|
| 数据 | 16 个关节角 | 16 个分段四元数（世界系 + local） |
| 骨长恒定 | 结构保证 | 不保证 |
| 反屈 / 手指自转 | 不可能出现 | 可能出现 |
| 忠实还原测量 | 受解剖模型约束 | 完全忠实（含不合理姿态） |
| 需要 ROM 标定 | **是** | 否 |
| 驱动机械臂 | **只能用这个** | 不适用（伺服只吃角度） |
| 上手难度 | 要跟绑定姿势对齐旋转轴 | 直接赋 localRotation |

**建议先用 Quaternion 模式确认链路通了**（最少的假设、最直观），
再切到 JointAngles 调旋转轴——那个是最终要用来驱动机械臂的。

## 只赋 rotation，不要赋 position

四元数是【朝向】，不是位置。绑定时：

- **朝向** → `bone.localRotation`
- **位置** 由骨骼层级和骨长自动决定，**除手腕根节点外都不要赋值**

给每根骨头都赋位置会把骨骼拉断。

另外确认你的模型结构：这里发的是 **1 手腕 + 5 指 × 3 节 = 16**。
很多 Unity 手模型每指有 4 节（多一个掌骨）或带 tip 骨 —— 不对应的话要先做一次映射。

## 骨骼数组顺序（16 段）

```
0            手腕
1,2,3        拇指  近节/中节/远节
4,5,6        食指
7,8,9        中指
10,11,12     无名指
13,14,15     小指
```

没有的骨骼留空，会被自动跳过。

## 三个可能需要你改的地方

**1. 模型朝向不对** → 改 `ConvertQuat` / `ConvertPos`。
发送端是右手系、毫米、+Z 朝手背；Unity 是左手系、米、+Y 朝上。
换算故意放在 C# 侧——发送端不知道你的骨骼绑定姿势，这边知道。**不用改 C++。**

**2. 手指弯错方向**（仅 JointAngles 模式）→ 改 `ApplyFinger` 里的旋转轴或符号。
默认是"屈曲绕 X、外展绕 Y"，这是最常见的一种绑定约定。

**3. 手指抖或出现奇怪姿势** → 打开 `skipUnmeasuredSegments`（默认已开）。
它会跳过 `segSource < 2` 的分段，也就是**两端点都是网络补出来的**那些。
关掉会更跟手，但你会看到猜出来的姿态。

## 绑骨骼前先用监视器看数据

```
python tools/unity/udp_monitor.py --port 9010
```

逐关节实时打印，带中文名和来源标记：

```
分段      来源          local四元数 (w,x,y,z)         等效欧拉角(度)
手腕      ✓ 几何测的     0.997  0.075  0.000  0.000     8.6   0.0   0.0
食近节    ★ IK解的       0.995  0.100  0.000  0.000    11.5   0.0   0.0
食远节    ? 网络猜的     0.975  0.223  0.000  0.000    25.8   0.0   0.0
小远节    ✗ 无依据       0.900  0.435  0.000  0.000    51.6   0.0   0.0
```

关节角那一栏还带条形图，弯手指时能直接看出哪个关节在动、往哪个方向动。

**为什么先看这个再绑骨骼**：模型不动可能是没数据、可能是骨骼没绑对、也可能是
数据全被判为不可信而跳过了 —— 这三种在 Unity 里长得一模一样，在监视器里一眼可分。

**注意**：UDP 单播同一端口【只有一个进程能收到】。调试时先关掉 Unity 用监视器看，
确认数据没问题再开 Unity。

## Inspector 里的诊断字段

- `packetsReceived` —— 收到包数，不涨说明网络没通
- `wristPoseValid` —— 手背点够不够解腕部位姿
- `mcpValid` —— 掌指角是新算的还是保持上一帧
- `validFingers` —— 本帧有几根手指的角是新算的（0~5）

**实测预期**：手摊开 4.9/5 指，自由动作约 3.4/5 指。
低于这个数说明遮挡比预期重，看 `wristPoseValid` 是不是经常掉。

## 关于 roll（用 Quaternion 模式前请读）

每节指骨只贴了一颗反光球，**绕骨轴的自转在数学上不可观测**。
四元数里那一维是发送端用手背法向填出来的，不是测量值。
手摊开时看不出来，手指弯曲时可能看到轻微的"拧"。

JointAngles 模式天然没有这个问题——铰链只有一个自由度，roll 由骨骼层级推出来。
要真实的 roll，只能每节贴第二颗球。

## 包格式（自己写解析的话）

小端，float32。前 3 字节都是 `M3D`，第 4 字节区分类型。

```
M3DS  124 字节
  magic(4) ts_ns(i64) wristPos(3f) wristRot9(9f) jointAngles16(16f)

M3DQ  556 字节
  magic(4) ts_ns(i64) flags(u32) wristPos(3f)
  segQuatWorld[16](64f)   (w,x,y,z) 世界系
  segQuatLocal[16](64f)   (w,x,y,z) 相对父节点
  segSource[16](16B)      0=None 1=Predicted 2=Geometry 3=IK

  flags: bit0 wristPoseValid, bit1 mcpValid, bit8..12 五指关节角本帧有效
```

两个包都在 UDP 单包上限内，不会分片。
